## 3. 程式碼可確認與不可確認事項

### 可確認

- 首頁導覽有上述多個功能入口。
- 管理後台存在 17 個功能分頁。
- 管理後台載入流程目前呼叫儀表板、網站內容、公告、商品、訪客、優惠券、活動／比賽、快速連結及客服等資料載入函式。
- 目前讀取到的 `admin.js` 與 `app.js` 內容沒有出現 maintenance／維護系統實作。
- 網站已存在台北時間處理 helper：管理端活動時間欄位轉 ISO 時使用 `+08:00`。維護系統應沿用明確時區策略，避免瀏覽器本地時區造成時間偏移。

### 尚不可確認

- 使用者先前所說「七個維護範圍」的正式名稱及代碼。
- 七個範圍是依前台頁面、後台模組、服務/API、或其他產品分區切分。
- 全站維護是否算在七個範圍內，或是額外的第八種控制。
- 每個頁面是否需要獨立維護，還是應將數個頁面合併為一個維護範圍。
- 維護時是否仍允許管理員登入與使用管理後台。
- 維護提示要顯示在哪些頁面，以及登入頁、個人中心、App 更新頁是否受影響。

## 4. 候選分組（僅供討論，尚非正式 scope）

依網站入口與管理功能，可先考慮下列候選領域；這些分組不是既定答案：

| 候選領域 | 程式碼可見的功能例子 | 待確認 |
|---|---|---|
| 網站核心 | 首頁、網站內容、快速連結 | 是否獨立成範圍 |
| 公告與資訊 | 最新消息、公告管理、行事曆、AI 公告 | 行事曆是否併入公告 |
| 活動與比賽 | 活動／比賽、達人榜、報名與簽到 | 是否整合成單一範圍 |
| 影音內容 | 影音頻道 | 是否獨立 |
| 會員與成長 | 訪客帳號、個人中心、會員成長、獎勵、優惠券、通知 | 是否拆成會員／獎勵兩個範圍 |
| 商城與客服 | 商品、訂單、客服中心 | 客服是否獨立 |
| 下載與 App | 檔案下載、App 更新、App 設定 | 是否合併為一個範圍 |

注意：上述候選恰好列出七個領域，只是為了方便討論，並非從資料庫或現有規格證明原本七個 scope 就是這七項。若使用者原先已有七項定義，必須以使用者確認為準。

## 5. 維護模式與後台存取建議

初步建議把「全站維護」視為覆蓋規則，而不是把管理後台與其他前台頁面一起鎖死：

- 訪客：看到維護提示與預計恢復時間。
- 一般登入使用者：依維護範圍看到提示；未受影響的範圍仍可使用。
- 管理員：可登入管理後台、查看維護事件、調整或解除維護。
- 維護狀態 API：只公開顯示所需欄位，不回傳內部備註與稽核資料。
- 若維護的是登入／認證服務本身，管理員登入也可能受影響；這需另設緊急處理方案，不能只靠同一登入服務保證可解除維護。

以上屬於建議方案，尚待產品確認。

## 6. 時間與時區核對

目前 `admin.js` 已有台北時間 helper，將 datetime-local 值以 `+08:00` 轉成 ISO 時間。維護系統建議：

- DB 一律存 `timestamptz)，代表明確時間點。
- API 使用 ISO 8601 UTC 時間傳輸。
- 管理端顯示及輸入使用 `Asia/Taipei`。
- 不允許用戶端自行提供「現在時間」決定事件是否生效；生效狀態以伺服器／資料庫時間判斷。

此為建議設計，實作時仍需測試台灣時區與跨時區瀏覽器。

**在建立 scope seed、資料庫 constraint 或 migration 前，必須先取得使用者對七個範圍的確認。**

建議先確認候選分組是否符合原先構想，再決定：
1. 七個正式範圍的名稱與穩定代碼。
2. 全站維護是獨立控制，還是第八個 scope。
3. 全站維護時管理員後台是否維持可用。
4. 各範圍對應哪些前台頁面及後台模組。
5. 維護期間頁面應完全封鎖，還是只顯示警示並保留唯讀功能。
