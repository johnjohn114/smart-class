> Scope: public application schema only. No production writes, DDL, migration, deployment, or settings changes.

## 1. Executive result

The 2026-11-08 public catalog snapshot is substantially consistent with the 2026-11-25 production `public` schema for the object classes compared below. The earlier apparent 8-column drift was a counting mismatch: 412 table columns plus 8 view columns equals 420 public relation columns on both sides.

**No differences were found** in the 44 table columns' names, types, nullability, defaults, or identity settings; the 150 constraints; the 49 explicit indexes (plus 60 constraint-backed indexes); the 98 RLS policy definitions; the 45 relation owners/ACLs; or the 38 function body sections and captured function metadata.

This is a **catalog compatibility comparison**, not a restorable baseline. It does not make the 2026-11-08 snapshot a complete `pg_dump --schema-only` file and does not resolve the empty production migration ledger.

For all 412 table columns, comparison covered:

**Differences: 0.**

The `device_push_tokens.id` column is `GENERATED BY DEFAULT AS IDENTITY` in both environments. The snapshot parser initially treated the word `DEFAULT` inside that identity clause as a column default; this was corrected by interpreting identity separately. The live identity sequence is `device_push_tokens_id_seq`.

The view `activity_member_stats` exposes 8 columns with matching names and data types. Its deparsed SQL text differs in formatting/parentheses from the catalog-reconstructed snapshot; this audit confirms the output-column shape, owner/ACL metadata, and current view options, but does not claim an independent semantic AST equivalence proof for the view query.

## 3. Constraints, indexes and policies

| Object | Snapshot | Production | Result |

The 49 explicit index definitions were compared with `pg_get_indexdef`; the 150 constraint definitions were compared with `pg_get_constraintdef`. After normalizing whitespace, quoting and schema qualification, no definition differences were found.

The policy comparison parsed all 98 statements and compared policy table/name, permissive mode, command, role list, USING expression and WITH CHECK expression against `pg_policies`. No differences were found.

All 44 public tables have RLS enabled in production, and none currently has FORCE RLS. The snapshot records RLS enabled for all 44 tables. This is an observation only; no RLS setting was changed.

Function-body comparison is limited to the body sections plus the separately compared metadata above; it is not a claim that every PostgreSQL catalog attribute or external dependency is represented in the snapshot.

The 2026-11-08 snapshot records the sequence parameter inventory and owner, but does **not** record the `OWNED BY` dependency. It also does not provide a complete sequence reconstruction/ownership script. This remains a known gap to fix in a future complete schema-only export. Sequence current values are not part of this schema compatibility comparison.

## 7. Why this is still not a complete baseline

The repository snapshot explicitly covers public application objects, not every production schema or managed service dependency. The production inventory includes objects in `auth`, `storage`, `realtime`, `vault`, `extensions`, `graphql` and `graphql_public` in addition to `public`.

The snapshot does not provide a complete, restorable capture of:
- Supabase-managed Auth, Storage, Realtime and Vault schemas.
- All installed extensions and their dependencies.
- All schema owners/ACLs and role memberships outside the captured public scope.
- Global and schema-specific default privileges for every owner/schema.
- Sequence ownership dependencies and all restore-order details.
- Every object class, dependency, comment, publication, subscription, policy and managed-service configuration required for a faithful full-project reconstruction.

The production migration list remains empty, and `supabase_migrations.schema_migrations` is still absent. Structural matching does not prove that any particular historical migration file was applied.
